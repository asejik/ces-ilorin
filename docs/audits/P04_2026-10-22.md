# P04: Security Audit (re-run)

**Date**: 2026-10-22 · **Project**: CES Portal · **Rigor level**: STRICT (public site, personal data incl. passport photos, NDPA 2023, hostile-user assumption)
**Method**: code review + live black-box tests against the real Supabase project using only the public anon key (the same power any visitor has) + production-build inspection + `npm audit`. All write tests were designed to fail harmlessly (fake foreign keys) or were cleaned up immediately.
**Supersedes**: `P04_2026-09-19.md` (see section 8).

---

## 1. Context

**Sections audited**: 1 Authorization & data access, 2 Secrets, 3 Authentication, 4 Injection/input, 5 Business-logic abuse, 8 Files & storage, 9 Abuse protection & config, 10 Dependencies.
**N/A**: 6 Payments (none in v1), 7 AI features (none).

### Threat model
- **Assets**: student personal data (contacts, addresses, spiritual background, passport photos), academic integrity (scores, attendance, graduation status, certificates), exam content, admin powers, the church's email sender reputation.
- **Attackers**: a curious student; a student who wants a better grade or graduation; an outsider scraping personal data; a bot/spammer; a former or low-privilege staff member.
- **Attack surface (every entry point)**:
  - Public pages/actions: `/register` (`registerStudentAction`), `/assess` (`getAvailableQuizzesAction`, `verifyAssessmentAccessAction`, `submitAssessmentAction`), `/attendance` (`submitAttendanceCheckinAction`), `/certificate/[matricNo]` (`getCertificateByMatricAction`), `/register/success`, `/api/health`.
  - Staff area: `/login` (Supabase Auth), `/admin/{gradebook,broadsheet,attendance,quizzes}` and their Server Actions.
  - Supabase directly: REST/PostgREST on `ces_*` tables with the **public anon key** (shipped in the browser bundle by design), Auth endpoints, Storage buckets `ces-assets` (public), `ces-private`, `artwork` (not ours).
  - Next.js image optimizer `/_next/image`.

---

## 2. Top 5 fixes (biggest impact for effort)

1. **P04-01 + P04-02** – One Supabase migration: remove the anonymous read of quiz PINs and the "anyone can insert" policies, and revoke blanket `anon` grants. This closes the two CRITICAL holes.
2. **P04-04** – Make passport photos private (signed URLs, random file names).
3. **P04-03 + P04-05** – Protect attendance with a class code, and add rate limiting/CAPTCHA to the public actions.
4. **P04-06** – Upgrade `next` (to ≥ 15.5.24), `nodemailer`, replace `xlsx`.
5. **P04-07 + P04-08** – Restrict the image optimizer and disable open sign-ups.

## 4. Findings in detail

### P04-01 · CRITICAL · Authorization: PINs readable by anyone

> **STATUS: FIXED and VERIFIED (2026-10-22).** Migration `20261022_p04_lockdown_anon_access.sql` applied by the owner in the Supabase SQL editor (scoped to `ces_*` tables only). `npm run test:rls`: **17/17 checks pass** (was 5 failures): anon reads of all eight tables blocked (`42501`), no session PIN visible, anon inserts into students/attendance/assessments/quizzes/certificates refused (`42501`, no longer reaching the FK check), update/delete no effect. **App flows re-tested after the change** against a local production build: registration (new student created, email via dev mock), quiz entry with wrong then correct PIN, quiz submit (score recorded), attendance check-in and duplicate block, staff login, gradebook (cohort switch, score override recording the staff id), broadsheet (graduate/distinction, certificate preview), quiz PIN manager and attendance analytics all work. Rollback script: `supabase/migrations/20261022_p04_lockdown_anon_access_rollback.sql` (re-opens the holes; do not use except to restore service).
- **Location**: `supabase/migrations/20260918_init_schema.sql` — `CREATE POLICY "Public can view open quizzes" ON ces_quizzes FOR SELECT USING (is_open = true OR is_ces_staff());` plus `GRANT ALL … TO anon`. The `session_pin` column lives in the same table.
- **Live evidence** (anon key, no login): `SELECT ces_quizzes` returned **18 rows including `session_pin`**, and the value equalled the real PIN (`anon PIN == real PIN: true`). This is *after* I rotated the PINs, so rotation alone does not fix it.
- **Impact**: the "Teacher Session PIN" that proves a student is physically in class is public. CLAUDE.md rule 4 (Assessment Access Security) is defeated.
- **Attack scenario**: (1) open the site, copy the anon key from the JS bundle or network tab; (2) call `GET /rest/v1/ces_quizzes?select=course_code,session_pin&is_open=eq.true`; (3) go to `/assess`, type any classmate's matric number and the PIN; (4) answer on their behalf, or submit junk to burn their single allowed attempt.
- **Minimal complete fix**: (a) replace the public SELECT policy with staff-only (`USING (is_ces_staff())`); the app already reads quizzes through the service-role server action, so nothing legitimate breaks; (b) do the same check for any other table with an `anon` SELECT policy (`ces_semesters` is intentionally readable and has no secrets); (c) rotate PINs again after the policy change; (d) re-run the self-test below.
- **Safe self-test**: `curl "<SUPABASE_URL>/rest/v1/ces_quizzes?select=course_code,session_pin" -H "apikey: <ANON_KEY>" -H "Authorization: Bearer <ANON_KEY>"`. Expected after fix: `[]`.

### P04-02 · CRITICAL · Authorization: anonymous writes accepted
> **STATUS: FIXED and VERIFIED (2026-10-22)** by the same migration; see P04-01.
- **Location**: same migration — `CREATE POLICY "Anyone can register (insert student)" ON ces_students FOR INSERT WITH CHECK (true);`, `"Anyone can insert attendance" ON ces_attendance_records … WITH CHECK (true)`; and `20260918…` / `20260919_fix_permissions_and_seeds.sql`: `GRANT ALL ON ALL TABLES/ROUTINES/SEQUENCES … TO anon, authenticated, service_role` plus `ALTER DEFAULT PRIVILEGES … GRANT ALL`.
- **Live evidence**: anon `INSERT` into `ces_students` and `ces_attendance_records` with deliberately fake foreign keys failed with `23503` (foreign-key violation), which only happens **after** row-level security has allowed the insert; inserts into `ces_student_assessments` and `ces_quizzes` were correctly refused (`42501`). No rows were created.
- **Impact**: the Server Actions' validation (Zod, cohort checks, throttles, matric generation, duplicate check) is bypassable by calling the database directly. An attacker can create fake students with any matric number, status or cohort, then (using P04-01) take quizzes as them. Fake rows appear on the gradebook and broadsheet and can reach "GRADUATE".
- **Fix**: drop both `WITH CHECK (true)` policies (registration and attendance already run through server actions using the service role, which bypasses RLS); `REVOKE ALL ON ALL TABLES/ROUTINES/SEQUENCES IN SCHEMA public FROM anon, authenticated` for the `ces_*` objects, then grant back only what is needed (likely `SELECT` on `ces_semesters` for `anon`); remove the over-broad `ALTER DEFAULT PRIVILEGES`. Ship with a rollback script.
- **Safe self-test**: `curl -X POST "<URL>/rest/v1/ces_students" -H "apikey: <ANON>" -H "Content-Type: application/json" -d '{"semester_id":"00000000-0000-0000-0000-000000000000", …}'`. Expected after fix: `401/403` or `42501`, **not** `23503`.
- **Same pattern elsewhere**: `ces_attendance_records`, any future table (the default-privilege rule applies to all).

### P04-03 · HIGH · Business logic: attendance needs no secret
- **Location**: `src/actions/attendance.ts` `submitAttendanceCheckinAction` — input is matric number, course, date, rating; nothing proves presence.
- **Impact**: "Attended" for both Elementary Principles and Membership & Vision is a graduation condition (CLAUDE.md rule 2). Matric numbers are sequential (`CES/ILR/26I901`, `…I902`), so anyone can mark attendance for any student, or lock a real student out (their own check-in is then rejected as a duplicate).
- **Attack scenario**: loop over `CES/ILR/26I901…26I999` on the public form/action with course "Elementary Principles".
- **Fix**: require a per-class code set by the teacher (like the quiz PIN, kept server-side), plus rate limiting (P04-05); add an unguessable student secret (e.g. surname + last 4 phone digits) as a second factor if you want stronger identity.
- **Safe self-test**: check in with a classmate's matric number from an incognito window; it should be refused without the class code.

### P04-04 · HIGH · Passport photos are public
- **Location**: `src/actions/register.ts` uploads to bucket `ces-assets` at `passports/<matric>.jpg` and stores `getPublicUrl()`; bucket is **public** (verified via bucket list), cacheControl one year.
- **Live evidence**: `GET <public url>` with no credentials → **HTTP 200 image/jpeg** for `CES_ILR_26I901.jpg`. Directory listing as anon returned 0 files (good), but paths are predictable from matric numbers.
- **Impact**: identifiable faces of students downloadable by anyone who can guess `CES_ILR_26<letter><digit><nn>.jpg`; NDPA 2023 data-minimisation/confidentiality concern.
- **Fix**: make the bucket private; store only the object path; generate short-lived signed URLs server-side for staff pages and the certificate; name files with random UUIDs instead of matric numbers; migrate existing files. (The 1-year cache means already-fetched copies may persist in caches.)
- **Self-test**: open the photo URL in a private window; expected after fix: 400/403.

### P04-05 · HIGH · No rate limiting / abuse protection
- **Evidence**: grep for any limiter/throttle in `src/` finds only the 60-second same-email check in `register.ts`.
- **Impacts**: (a) **Enumeration oracle**: `verifyAssessmentAccessAction` answers "No registered student found with matric number …" vs "Incorrect Session PIN", so valid matric numbers can be harvested; (b) **email abuse**: any address can be typed into the registration form, causing the church's Gmail account to send welcome mail to a victim; different emails bypass the 60 s check, risking the sender account being rate-limited/blocked; (c) unlimited registrations burn matric numbers and fill the database; (d) brute force on any future secret (class codes).
- **Fix**: per-IP and per-matric rate limits (e.g. Upstash Redis / Vercel KV, or a small Supabase table); Cloudflare Turnstile (free) on `/register`; return one generic error for "unknown student or wrong PIN".
- **Self-test**: submit the access form 20 times in a minute with wrong PINs; after the fix you should be throttled.

### P04-06 · HIGH · Vulnerable dependencies (`npm audit`)
- **Evidence**: `21 vulnerabilities (5 moderate, 13 high, 3 critical)`. Production dependencies: `next@14.2.35` — advisories fixed only in 15.5.x/16 (image-optimizer RCE with AVIF `<15.5.24`, server-action DoS and SSRF `<15.5.21`, RSC cache poisoning `<15.5.16`, middleware-redirect cache poisoning, request smuggling); `nodemailer@6.10.1` — SMTP/header injection and recipient-domain validation bypasses (the app passes the user-typed email to `sendMail`); `xlsx@0.18.5` — prototype pollution and ReDoS, **no npm fix** (only used to write exports; low exposure); `postcss`, `source-map-js` (build-time). Dev-only: `vitest/tinypool` (critical, dev machines only).
- **Fix**: upgrade Next to ≥ 15.5.24 (App Router; test route handlers/Server Actions), `nodemailer` to the current major, replace `xlsx` with the maintained SheetJS CDN build or `exceljs`, `npm audit fix` for the rest; keep `npm audit --omit=dev` in CI.
- **Note**: Windows-only RCE advisories do not apply to Vercel (Linux) hosting; the image-optimizer and server-action issues do.

### P04-21 · HIGH · Public certificate lookup exposed results (added 2026-10-23; **FIXED 2026-10-23**)
- **Location**: `getCertificateByMatricAction` (`src/actions/broadsheet.ts`) used by `/certificate/[matricNo]`: no login, looked up by sequential matric number, and **issued a certificate on demand**.
- **Impact**: anyone could read a student's name, total score and honours class, contrary to the rule that students do not view results.
- **Fix**: action now calls `requireStaffUser()`; middleware also protects `/certificate/*`.

### P04-19 · HIGH (residual) · Exam content previously public
- Question text, correct answers and default PINs were committed to a public GitHub repo from Sep 2026. History was rewritten and force-pushed, but GitHub still serves the old commit SHAs on direct request (verified), and anyone who cloned earlier keeps a copy. **Owner decision (2026-10-22): keep the current repo.** Practical consequence: treat the current question bank as compromised; write fresh questions before the next cohort's graded assessment, and keep PINs rotating. Optional: ask GitHub Support to purge cached commits, or recreate the repository.

### P04-20 · MEDIUM · Schema-wide grants in a shared project (added 2026-10-22 after the owner confirmed the project is shared)
- **Location**: `20260918_init_schema.sql` section 11 and `20260919_fix_permissions_and_seeds.sql`: `GRANT ALL ON ALL TABLES IN SCHEMA public …`, `GRANT ALL ON ALL ROUTINES IN SCHEMA public …`, `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL …` to `anon, authenticated, service_role`.
- **Impact**: these statements are not limited to `ces_*`. Any table or function in `public` that belongs to the other application (same church, sermons app) received the same grants (Supabase's own defaults are similar, so the practical change may be small, but it was not CES's decision to make). Whether the other application is exposed depends on its own RLS, which this audit did not and should not inspect.
- **Fix**: (a) the new lockdown migration is strictly scoped to the eight `ces_*` tables and does not touch defaults; (b) ask the other project's owner to review their table privileges/RLS (query 4 in `supabase/verify/p04_pre_check.sql` lists table names and RLS flags only); (c) long term, give CES its **own Supabase project** (also resolves P03-04, P04-08, quota sharing in P02).
- **Note**: all tests in this audit read or wrote only `ces_*` tables and the CES buckets; no other application's data was queried.

### P04-07 · MEDIUM · Open image proxy
- **Location**: `next.config.mjs` `images.remotePatterns: [{ protocol: 'https', hostname: '**' }]`.
- **Live evidence**: `/_next/image?url=https://www.google.com/favicon.ico` → **HTTP 200**. Any https image on the internet can be fetched and cached through the app (bandwidth/egress cost, SSRF-style probing, link laundering).
- **Fix**: allow only the Supabase storage hostname, or remove `remotePatterns` (the only `next/image` use is a local `data:` preview).

### P04-08 · MEDIUM · Open sign-up on shared Auth
- **Evidence**: `/auth/v1/settings` → `disable_signup: false`, providers: email. The Supabase project is shared with other apps (`artwork` bucket), so their users are also `authenticated` here.
- **Impact**: anyone can create an account. `src/lib/supabase/middleware.ts` only checks that a user exists before showing the `/admin/*` pages; data is still protected by `requireStaffUser()` and `is_ces_staff()` (verified), so exposure is the admin UI shell, plus any future policy written as `TO authenticated`.
- **Fix**: disable public sign-ups in the Supabase dashboard (create staff via invite); make the middleware check the staff role, not just a session.

### P04-09 · MEDIUM · Public certificate lookup
- **Location**: `getCertificateByMatricAction` in `src/actions/broadsheet.ts` (no auth, by design for verification): `.ilike('matric_no', cleanId)` / `.ilike('certificate_no', cleanId)` returns full name, passport URL, matric, cohort, score, honour.
- **Impact**: guessable identifiers + unescaped `%`/`_` wildcards allow enumeration of graduates and their scores and photos.
- **Fix**: verify by an unguessable certificate code, return only "valid + name + class", escape wildcard characters (use `.eq` after normalising), rate limit.

### P04-10 · MEDIUM · No role separation, weak override integrity, no audit trail
- **Location**: every call is `requireStaffUser()` with **no role list** (so a `ces_teacher` can issue certificates, change PINs, read all personal data). `scoreOverrideSchema` (`src/lib/validation/attendance.ts`) lets the browser send `maxScore` and accepts any `newScore ≤ 60`, never checking the quiz's real `max_score`: a 5-mark quiz can be overridden to 60. The update overwrites the previous score, the insert path never records `overridden_by`, and there is no append-only log.
- **Fix**: role matrix (teachers: scores/attendance; admins: certificates/PINs/export); read `max_score` from `ces_quizzes`; add an append-only `ces_audit_log` (who, what, old → new, reason, time) that staff cannot edit; add DB `CHECK (score <= max)` via trigger.

### P04-11 · MEDIUM · Open redirect
- **Location**: `src/app/(auth)/login/page.tsx` line 35–36: `router.push(params.get('redirect') || '/admin/gradebook')`.
- **Scenario**: a phishing link `…/login?redirect=https://evil.example` sends staff to an attacker page right after they authenticate on the real site.
- **Fix**: accept only values that start with a single `/` and not `//` or a scheme.

### P04-12 · MEDIUM · Submission checks
- **Location**: `submitAssessmentAction`: `if (expectedPin && (!sessionPin || sessionPin !== expectedPin))` — a quiz with an empty PIN is submittable without one; the quiz's semester is never compared with the student's. A student can submit to a quiz id from the other cohort.
- **Fix**: require a non-empty stored PIN; verify `quiz.semester_id === student.semester_id`; keep the `UNIQUE(student_id, quiz_id)` guard (verified present).

### P04-13 · LOW · CSP and headers
- Live headers present: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, CSP. But CSP has `script-src 'unsafe-inline' 'unsafe-eval'` and `img-src https:`, and `X-Powered-By: Next.js` is sent. **Fix**: nonce-based CSP in middleware, drop `unsafe-eval` in production, `poweredByHeader: false`. HSTS not verified (depends on the production host).

### P04-14 · LOW · Raw errors returned
- Examples: ``Failed to record score: ${insErr.message}``, ``Database save error: ${insertErr.message}``, catch blocks returning `err.message`. **Fix**: log server-side, return generic text.

### P04-15 · LOW · PII in URL
- `/register/success?matricNo=…&name=…&cohort=…` puts a name and matric number in the URL (history, logs, referrers); anyone can also craft a fake success page. **Fix**: render from a short-lived signed cookie.

### P04-16 · LOW · Function hardening
- `is_ces_staff()` is `SECURITY DEFINER` without `SET search_path = public`. **Fix**: add `SET search_path = public, pg_temp`.

- **Admin route guard**: unauthenticated `GET /admin/gradebook` → `307 /login?redirect=%2Fadmin%2Fgradebook`.

- **CSRF**: login uses Supabase cookies (SameSite=Lax by default) and Next Server Actions enforce same-origin; no custom state-changing GET routes.
- **404** pages return a real 404 status.

## 9. CLIENT SUMMARY (safe to share)
The CES portal is well organised, and staff-only pages and actions are properly protected. This review found two serious gaps in how the database is exposed to the public internet. First, the class passwords (PINs) that prove a student is in class can be read by anyone with technical knowledge; second, the database accepts some records directly from the public, bypassing the website's own checks. Student passport photos can also be opened by anyone who guesses the web address. None of these has been abused as far as we know, and the site has not yet been launched publicly. We recommend fixing these before launch: tightening database permissions, making photos private, adding a class code for attendance, limiting repeated requests, and updating several software components. Exam questions that were once visible in a public code repository should be refreshed before the next graded assessment. Fixes will be tested and applied step by step with your approval.
