## 4. Findings in detail

### P03-01 · HIGH · Matric number generation
- **Location**: `src/actions/register.ts` (~lines 117–128): `select count(*) from ces_students` then `sequence = (count || 0) + 1`, passed to `generateMatricNumber`. Photo uploaded **before** the insert with `upsert: true` at `passports/<matric>.<ext>`.
- **Problems**:
  1. **Race**: two simultaneous registrations read the same count and produce the same matric. The `UNIQUE(matric_no)` constraint makes the second insert fail, but by then its photo has **overwritten the first student's photo** (`upsert: true`), and the user sees "A student with this matric number or email already exists." — misleading.
  2. **Breaks permanently after any hard delete**: with students 1..5 and #2 deleted, `count + 1 = 5`, which already exists, so every new registration fails until a number is freed. (Soft-deleted rows keep counting, hard deletes do not.)
  3. **Not per-month**: the spec example `CES/ILR/26H801` reads "August 2026, 1st student"; the code uses the global total (existing live data: `…26I901`, `…26I902` — consistent with either reading). **Please confirm with the client** whether the sequence resets each month.
  4. CLAUDE.md rule 3 requires atomic generation at registration.
- **Fix**: create a Postgres function (e.g. `ces_register_student(...)`) that takes a lock/uses a counter table keyed by `(yy, month)` and inserts the student in one transaction; upload the photo **after** the insert using a random file name and `upsert: false`; return the real constraint message.
- **Same pattern elsewhere**: none other found.
- **Verify yourself**: with a second terminal, submit two registrations in the same second after the fix; both must get distinct matric numbers and photos.

### P03-02 · HIGH · Hardcoded semester id
- **Location**: `src/app/admin/gradebook/_components/use-gradebook.ts` — `HARDCODED_SEMESTER_ID = '8b3ade26-…'` (the Regular 2026 semester). `handleToggleAttendance` passes it to `overrideStudentAttendanceAction` for **every** student.
- **Impact**: toggling attendance for a Sunday Cohort student writes (or creates) an attendance row in the **Regular** semester. The Sunday student's broadsheet never changes, then the next refresh reverts the optimistic UI. Graduation clearance for the Sunday Cohort cannot be corrected by staff.
- **Fix**: use the `semesterId` returned with each gradebook row (or derive it server-side from the student). Add a unit test.
- **Live reproduction (2026-10-22)**: logged in as a temporary staff user, opened the Sunday tab, toggled "Elem Princ" for the Sunday student `CES/ILR/26I902`. The database then held an `Elementary Principles = Attended` row in **"Regular Cohort — 2026"**, while the Sunday gradebook still showed "Unmarked". (One stray test row remains in the live test data until your reset.)
- **Verify**: toggle a Sunday student's "Elem Princ" and refresh; the value must persist.

### P03-04 · HIGH · No environment separation, test data in the live database

### P03-07 · MEDIUM · Email address handling
- `email_address TEXT NOT NULL` with no `UNIQUE` (schema line 42), yet `register.ts` returns "A student with this matric number or email already exists" for code `23505`, which can only come from the matric constraint. The same person can register repeatedly after the 60-second window.
- `sendWelcomeEmail` is awaited inside registration: no timeout, no retry; if it fails the student still sees success and nothing is stored, so staff cannot tell who never received the manual or matric number.
- **Fix**: case-insensitive unique index on email (after de-duplicating), an `email_status` column or outbox table, SMTP timeout, and a "resend" button for staff.

### P03-08 · MEDIUM · Monitoring
- No error tracker (Sentry or equivalent), no uptime monitor, no alerts. 17 `console.error` calls log raw database error objects, which can contain row values (e.g. "Key (email)=(…) already exists").
- `/api/health` returns `ok` without touching the database, so it cannot detect an outage of the part that matters.
- **Fix**: add Sentry (free tier) with PII scrubbing; make `/api/health` run a trivial `select 1` through the service client; add a free uptime monitor (e.g. UptimeRobot) with email alerts.

### P03-09 · MEDIUM · Backups / continuity (NOT VERIFIED)
- Supabase plan tier is not known to me. On the free tier there are no downloadable point-in-time backups, and projects that receive no traffic for ~7 days are paused, which is a real risk for a school that meets weekly. No restore has been tested.
- **Fix**: confirm plan; schedule a weekly `pg_dump`/CSV export of `ces_*` tables to storage you own; do one trial restore into the staging project before launch.

### P03-10 · MEDIUM · Compliance (NDPA 2023)
- The consent checkbox is validated but **not stored**: no consent timestamp or policy version is saved with the student. There is no privacy notice page (only the checkbox sentence), no documented way for a student to access, correct or erase their data, no retention rule, and no append-only audit log of staff actions (P04-10). Passport photos are publicly reachable (P04-04).
- **Fix**: add `consent_at` / `consent_version` columns; publish a privacy page and contact for data requests; define retention (for example, delete photos and contact data N months after graduation); build the audit log.

### P03-11 · MEDIUM · Time zone
- Attendance defaults use `new Date().toISOString().split('T')[0]` (UTC) in `attendance.ts` and `gradebook.ts`; `register.ts` takes the matric **month** from the server clock (`getMonth()`; Vercel runs in UTC). Nigeria is UTC+1, so a registration at 00:30 on the 1st gets the previous month in its matric number and an attendance check-in after 23:00 gets "tomorrow's" date rejected as "in the future" or the wrong day.
- **Fix**: compute dates in `Africa/Lagos` (e.g. `Intl.DateTimeFormat('en-CA', {timeZone: 'Africa/Lagos'})`); keep timestamps in UTC.

### P03-12 · MEDIUM · Cascading deletes
- `ces_student_assessments`, `ces_attendance_records` and `ces_certificates` use `ON DELETE CASCADE` on `student_id`: removing a student row deletes their grades, attendance and certificate. Combined with P03-01 (a deletion also breaks matric generation), this is a data-loss path.
- **Fix**: `ON DELETE RESTRICT` for academic records; use the existing `is_deleted` soft delete; give staff a "withdraw student" action.

### P03-17 · HIGH · Silent 1,000-row cap
- **Location**: `getCohortGradebookAction` and `getBroadsheetAction` fetch every score with `.from('ces_student_assessments').select(...).in('quiz_id', quizIds)` and no pagination. A cohort needs `students × 9` rows (8 quizzes + exam): 112 students already produce > 1,000 rows. Supabase's REST API returns at most `max_rows` (default 1,000) **without raising an error**.

- **Fix**: paginate with `.range()` in a loop (or fetch per quiz), or compute per-student totals in a SQL view/function; add a test with ≥ 150 seeded students; show a banner if a response length equals the cap.
- **Verify**: Supabase → Settings → API → Max rows; then load the broadsheet for a staging cohort of 150 students and compare the Excel row/score counts with a SQL count.
