## 4. Findings in detail

### P02-01 · HIGH · Passport photos are full-size
- **Evidence**: live storage listing: `CES_ILR_26I901.jpg` = **858,723 bytes**, `CES_ILR_26I902.jpg` = 18,267 bytes. `registerStudentAction` accepts any image ≤ 3 MB and uploads it unchanged (`src/actions/register.ts`; only size and magic-byte checks). The broadsheet shows each photo in a **32 × 32 px** box (`broadsheet-row.tsx`, `w-8 h-8`), and certificates show it larger — always the original file. Cache header is already 1 year (good), so repeat views on the *same* browser are free.
- **Impact (estimates)**: with the sample size (0.86 MB), one cold broadsheet load transfers ≈ **86 MB per 100 students, 520 MB for 600**. Opening it from a few devices/after clearing cache exhausts a 5 GB egress allowance. Storage: 600 photos × 0.86 MB ≈ **520 MB** (half the 1 GB free storage); at the 3 MB maximum, the 1 GB cap is reached at about **330 students**.
- **Fix**: resize in the browser before upload (canvas to ≈ 400 px, JPEG quality 0.8 → typically 30–60 KB) and re-encode on the server (`sharp` is bundled with Next on Vercel); store a 96 px thumbnail for tables and the 400 px version for certificates; replace existing files with a one-off script. Also combine with P04-04 (private bucket + signed URLs).
- **Verify**: DevTools → Network on `/admin/broadsheet`: image rows should show tens of KB, not hundreds.

### P02-02 · MEDIUM · Manual fetched per registration
- **Location**: `src/lib/email.ts` `loadManualAttachment()` calls `storage.download()` for every email. Currently the file is a 930-byte placeholder; a real manual (5–15 MB is typical) would cost its size in egress **per registration** (600 × 10 MB ≈ 6 GB) and may be rejected or spam-filtered as a large attachment.
- **Fix**: cache the bytes in module memory per warm serverless instance, or email a link to a short-lived signed URL (egress only when someone clicks), or point to a token-gated download page. Keep the file under a few MB regardless.

### P02-03 · LOW · Auth round-trips
- **Evidence**: `src/lib/supabase/middleware.ts:64` `auth.getUser()` (a network call to Supabase Auth) for every matched request that carries a Supabase cookie; `src/lib/auth/guard.ts:22` calls `auth.getUser()` again plus a `ces_staff_profiles` query inside every admin action. Only staff have cookies, so volume is small.
- **Fix** (optional): verify the JWT locally (`getClaims()`/JWKS with asymmetric signing keys) in middleware, keep one authoritative check in the action. Trade-off: a revoked session stays valid until the token expires (≈ 1 hour). Do not build a custom session cache. Check Supabase's current docs for `getClaims` support in the pinned `@supabase/ssr` version.

### P02-04 · MEDIUM · Reload after every click
- **Location**: `use-gradebook.ts` `handleToggleAttendance` does an optimistic update **and then** `await loadGradebook()`; `handleSubmitScoreOverride` also reloads everything. Each reload runs staff auth + 5 queries returning every student, quiz, score and attendance row of the cohort.
- **Impact**: marking attendance for 100 students = 100 full reloads (≈ 100 × 5 queries and ≈ 100 × (students × ~10) rows).
- **Fix**: update just the changed row from the action's response (or trust the optimistic update and revalidate once after a pause); debounce rapid toggles.

### P02-05 · MEDIUM · Computation in JS, no pagination, row cap
- **Evidence**: `getCohortGradebookAction`, `getBroadsheetAction` load all students, all assessments (`.in('quiz_id', …)`), all attendance and compute totals/KPIs in JavaScript; there is no `.range()` anywhere (only one `.limit(100)` in the attendance feedback list). 9 assessments × N students rows are fetched: **cohort of ~112 students ⇒ > 1,000 rows**. Supabase's API returns at most `max_rows` (default 1,000) **without an error**, so scores could be silently dropped and students shown as PENDING — see P03-17.
- **Fix**: SQL views/functions that return per-student totals and KPI counts (small payload), plus `.range()` pagination or cursor paging for the roster; test with a seeded 600-student cohort.

### P02-06 · LOW · N+1 on quizzes page
- `getTeacherQuizzesAction`: for each of the 9 quizzes two `count` queries (submissions, questions) → 18 extra queries on every load of `/admin/quizzes` and each cohort tab change. **Fix**: one grouped query/RPC.

### P02-07 · MEDIUM · Open image proxy
- `next.config.mjs` allows `hostname: '**'`. Live test fetched `https://www.google.com/favicon.ico` through `/_next/image` (HTTP 200). On Vercel this consumes image-optimisation quota and bandwidth for traffic that is not yours. **Fix**: allow only your Supabase storage hostname (or none: the only `next/image` use is a local `data:` preview, and the tables use plain `<img>`).

### P02-08 · LOW · Middleware scope
- `src/middleware.ts` matcher covers every non-static path, so each visit to `/`, `/register`, `/assess`, `/attendance`, `/certificate/…` runs the 86.5 kB middleware bundle (counted as an invocation on Vercel). **Fix**: `matcher: ['/admin/:path*', '/login']`.

### P02-09 · LOW · Student entry burst
- `verifyAssessmentAccessAction`: student lookup, (cached) seeding check, quiz lookup, duplicate lookup, question fetch ≈ 5 sequential queries per entry; `getAvailableQuizzesAction` also runs whenever the cohort tab changes. 100 students entering within a minute ≈ 500–700 queries — fine for Supabase, but a single RPC would be faster and cheaper and is needed for the planned 100-user load test (P03-03).

## 5. Projection (ESTIMATES, assumptions stated)
Assumptions: per student per month ≈ 3 page visits of the public JS (≈ 110 kB each, cached afterwards ⇒ ≈ 0.3 MB), ≈ 15 server-action calls × 5 kB ≈ 0.08 MB, one welcome email (manual size **M**, assume 5 MB), one photo upload (ingress, free). Staff: broadsheet opened repeatedly on fresh devices; photo size **P** = 0.86 MB (today) or 0.04 MB (after P02-01). Plan limits as in section 1 (unverified).

| Users (students) | Vercel bandwidth / month | Supabase egress: photos in one cold broadsheet load (P=0.86 MB → 0.04 MB) | Manual in emails (M=5 MB) | Storage for photos |
|---|---|---|---|---|
| 100 | ≈ 0.04 GB | 86 MB → 4 MB | 0.5 GB | 86 MB → 4 MB |
| 600 (plan's 12-month scale) | ≈ 0.2 GB | **520 MB** → 24 MB | **3 GB** | **520 MB** → 24 MB |
| 1,000 | ≈ 0.4 GB | 860 MB → 40 MB | 5 GB | 860 MB → 40 MB |
| 10,000 | ≈ 4 GB | 8.6 GB → 400 MB (one load) | 50 GB | 8.6 GB → 400 MB |

**First limit to be hit** (free tiers): **Supabase egress**, driven by the manual attachment (≈ 3 GB at 600 registrations if M=5 MB) plus repeated broadsheet loads of full-size photos (≈ 0.5 GB each). **Supabase storage (1 GB)** is next if photos stay at 0.86–3 MB each (≈ 330–1,100 students). Vercel bandwidth is comfortably below its limit at planned scale.

## 8. CHECKED AND PASSED
- **No** polling, realtime channels, `select('*')`, base64 data in database rows (photos are stored in Storage, only a URL is in the row) or AI/third-party API calls on page load.
- Queries name specific columns. Quiz delivery is lean: the question bank averages **242 bytes/question** (5 questions per quiz) and a saved answer payload is **65 bytes**; students download questions once per attempt.
- `ces-assets` uploads carry `cacheControl: 31536000` (1 year) so repeat views are served from the browser cache.
- Public pages are statically generated (`○` in the build output) with CDN cache headers; first-load JS ≤ 115 kB for student pages; the OG image is 36 kB; `public/` has no large assets. Excel export is generated in the browser (no server cost).

## 12. CLIENT SUMMARY (safe to share)
At the planned size of the school the system is cheap to run, but two things would push it past the free allowances of the hosting services sooner than needed: the student passport photos are stored at their original size (about 1 MB each) and the welcome email carries the full course manual every time. Shrinking photos and sending the manual more efficiently will keep costs at zero for a long time and make the staff screens load faster, especially on mobile data.
